# V3 Over-Engineering Audit

> Read-only audit of the v2 codebase to find duplications, unjustified abstractions, and generalization opportunities. Performed by the `feature-dev:code-explorer` subagent on 2026-05-20. Drives the v3 simplification plan at `docs/superpowers/plans/2026-05-20-strider-v3-simplification.md`. 21 findings ordered by impact.

## F1. Salsa + its entire machinery (orchestrator_salsa.rs, 944 LOC)

- **Where:** `crates/strider-analyze/src/orchestrator_salsa.rs` (944 lines), `crates/strider-analyze/tests/orchestrator_salsa_parity.rs`, `orchestrator_salsa_incremental.rs`, `orchestrator_salsa_per_region.rs`, `crates/strider/benches/v1_vs_v2.rs`.
- **Current shape:** Full salsa dependency (`#[salsa::input]`, `#[salsa::tracked]`, `#[salsa::interned]`, `#[salsa::db]`, `salsa::Storage`) wrapping a `StriderDbImpl` that holds a `Mutex<HashMap>` content-cache, a per-region fingerprint query, and an external fixed-point driver `run_v2`. The module's own Phase-8c comments acknowledge the critical insight: "the `Mutex<HashMap>` content cache is what actually achieves the hit; salsa contributes dependency tracking that Phase 6 was supposed to use for per-region incrementality — but that was deferred." In practice `optimized_function` delegates to `run_v1_with_targets`, which runs the entire v1 pipeline inside salsa. `classify_unresolved_external` always returns `Vec::new()`, so the outer salsa loop always terminates after one query call.
- **Proposed v3:** Delete `orchestrator_salsa.rs` entirely. A `Mutex<HashMap<u64, Arc<BfgEntry>>>` content-keyed cache (already present in `StriderDbImpl`) is the real mechanism; extract it as a standalone `BfgContentCache` struct. Wire v3's single pipeline directly.
- **LOC saved (estimate):** ~1000 LOC (source) + three test files (~300 LOC) + bench (~100 LOC) = ~1400 LOC.
- **Risk:** Medium — `strider-py` uses `run_v2` in its Python-facing `run` entry point (`crates/strider-py/src/run.rs`). Must replace with the simpler content-cache path.
- **Why it's safe to do:** The `v1_baseline` and `v2_baseline` snapshot tests cover the output contract. `orchestrator_salsa_parity.rs` already proves the salsa wrapper produces identical BFGs to `v1/run`. Delete salsa, keep the `Mutex<HashMap>` if desired, point strider-py's `run` at the direct pipeline.

## F2. All egg infrastructure: egraph adapter + nine `*Egg` pass variants

- **Where:** `crates/strider-ir/src/egraph_adapter/` (three files: `language.rs`, `from_graph.rs`, `extract.rs`); `crates/strider-analyze/src/opt/constant_fold_egg.rs`, `known_bits_egg.rs`, `flag_cmp_canonicalize_egg.rs`, `if_cond_inversion_egg.rs`, `load_readonly_egg.rs`, `stack_store_detect_egg.rs`, `stack_load_forward_egg.rs`, `call_stack_arg_collect_egg.rs`, `function_arg_detect_egg.rs`; `crates/strider-analyze/src/opt/pipeline_v2.rs`.
- **Current shape:** Nine egg-based pass clones of the nine imperative passes, each documented as "NOT a replacement — built alongside." `IfCondInversionEgg`, `CallStackArgCollectEgg`, and `FunctionArgDetectEgg` are explicitly documented as not using the egraph at all ("faithful direct port"). `LoadReadOnlyEgg` and `StackLoadForwardEgg` use the egraph only to classify addresses then fall back to imperative chain walks. Only `ConstantFoldEgg`, `KnownBitsEgg`, `FlagCmpCanonicalizeEgg`, and `StackStoreDetectEgg` genuinely use `EGraph` saturation. `PipelineV2` wires these together in ~120 LOC; nine parity tests in `strider-analyze/tests/` total ~800 LOC verifying equivalence with v1.
- **Proposed v3:** Delete all nine `*Egg` pass files, `pipeline_v2.rs`, the `egraph_adapter` module, `egg` dependency in `strider-ir/Cargo.toml`, and all nine parity tests. Use only the imperative passes. The `v1_baseline` snapshots already pin the contract.
- **LOC saved (estimate):** ~3500 LOC across the nine egg passes + egraph adapter (~1200 LOC) + pipeline_v2 (~230 LOC) + parity tests (~1500 LOC).
- **Risk:** High — `PipelineV2` is the current production default (as of Phase 8.5c, `common::analyze` calls `analyze_v2`). Before deleting, must flip all call-sites back to the v1 imperative pipeline (or the new v3 single pipeline). The `v2_baseline` snapshots must be updated or replaced with v3 baselines.
- **Why it's safe to do:** `v1_baseline` and `pipeline_v2_parity.rs` prove both pipelines produce identical IR for every fixture. The three non-egg "egg" passes are already equivalent by construction. Dropping egg also eliminates the worst-case-exponential rewrite risk the user named.

## F3. `PipelineV2` struct replacing three `OptimizerPipeline` constructors

- **Where:** `crates/strider-analyze/src/opt/pipeline_v2.rs` (227 LOC); `crates/strider-analyze/src/opt/mod.rs` functions `stable_default_pipeline()`, `destructive_default_pipeline()`, `default_pipeline()`; `crates/strider-analyze/src/strider/pipeline.rs` with `build_stable_optimizer_pipeline()`, `build_destructive_optimizer_pipeline()`, `build_optimizer_pipeline()`.
- **Current shape:** Six pipeline constructors for what is semantically one optimizer: three in `opt` (stable/destructive/default) plus three on `Strider` (same decomposition but layered with CC-aware passes). Then a seventh: `PipelineV2` as a struct that duplicates all of the above but with egg passes. The stable/destructive split exists to protect `RegionIndex` pinned `NodeId`s during the strider orchestrator's indirect-branch fixed-point loop.
- **Proposed v3:** One `OptimizerPipeline` that takes a `RunPhase::Stable | RunPhase::Final` enum parameter, OR (simpler) just one pipeline whose passes are safe to call mid-iteration because v3 won't have an indirect-branch mid-iteration repin problem (the fixed-point closes before passing to the optimizer). Single public constructor `optimizer_pipeline(cc, rom) -> OptimizerPipeline`.
- **LOC saved (estimate):** ~350 LOC.
- **Risk:** Medium — affects the strider orchestrator's fixed-point loop design. Low risk if v3 converges CFG before lifting (no mid-iteration IR growth).
- **Why it's safe to do:** `optimizer_pipeline_subsets.rs` tests pin the stable/destructive partition.

## F4. `BuiltCallingConvention` / `BuiltCallingConventionParts` / `FunctionBuilderCC` — three identical structs

- **Where:** `crates/target/src/calling_convention/mod.rs:107-148`; `crates/strider-ir/src/function_builder_cc.rs:46-63`. Two `From` impls at mod.rs:361-391.
- **Current shape:** `BuiltCallingConvention` (private fields, accessor methods) and `BuiltCallingConventionParts` (public fields, used as an intermediate bag for `try_from_parts`) have nine identical fields. `FunctionBuilderCC` is a further reduction of those same fields (seven fields, missing `ret_val_regs_float`, `link_register_vn`, `syscall_number_vn`). Two `From<BuiltCallingConvention>` impls copy fields into `FunctionBuilderCC`. The `FunctionBuilderCC` split was created (Phase 1 Task 1.3c) to prevent `strider-ir` from importing `target`.
- **Proposed v3:** Delete `BuiltCallingConventionParts` (collapse to direct construction). Keep `FunctionBuilderCC` (it serves the dep-direction architectural goal).
- **LOC saved (estimate):** ~100 LOC.
- **Risk:** Low — purely structural.
- **Why it's safe to do:** Any miscount causes compile errors; CC tests verify invariants.
