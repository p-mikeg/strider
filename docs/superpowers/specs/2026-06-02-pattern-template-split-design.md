# Pattern / Template data-structure split — design (follow-up)

Date: 2026-06-02
Status: approved direction; **execute after the current strider-pattern rewrite is merged to master**
Origin: owner feedback during the strider-pattern rewrite — "the data structure for Pattern is
the same for Template. They require entirely different things and both builders don't need the
same API."

## Problem

The current rewrite uses **one** compiled type, `Pattern` =
`petgraph::StableDiGraph<PatVertex, PatEdge>` (`PatVertex = Node(PatNode) | Output(PatOutput)`),
for **both** matching and templating, with a single `BuilderCore` (a `template: bool` flag)
backing both `MatcherBuilder` and `TemplateBuilder`. Consequences:

- A **match** node carries dead build fields (`build: Option<TemplateKind>`, `build_ty`).
- A **template** node carries dead match fields (`node_limit`, `post_match`, `force_ordered`,
  predicate `KindSpec`s, output-vertex width/limit constraints).
- `rewrite_rule_runtime(lhs: Pattern, rhs: Pattern)` takes the *same type* twice though one is a
  query and the other a build recipe — no type-level distinction.

Matching is *inspection under constraints* (rich kindspecs/predicates, output width/type
constraints, commutative retry, cast walk-through, capture-**binding**). Templating is
*construction* (concrete `NodeKind`/`Fn`, output signature, inputs that are a sub-node or a
**resolved** capture, one bottom-up topo pass). Different needs; one type forces the union.

## Direction (approved)

Introduce a **generic bipartite graph** that owns only the mechanics both share, and instantiate it
two ways with distinct payloads and distinct, purpose-built builders.

```
/// Generic bipartite Node → Output → Node graph.
struct BiGraph<N, O> {
    inner: StableDiGraph<BiVertex<N, O>, BiEdge>,
    root: Option<NodeIndex>,
}
enum BiVertex<N, O> { Node(N), Output(O) }
enum BiEdge { Produces, Consumes { slot: usize } }
// Shared mechanics (generic): add_node, add_output, consume, set_root/root,
// reachable_topo (petgraph::algo::toposort + DfsPostOrder), assert_dag, node/output iteration.
```

- **`Pattern = BiGraph<PatNode, PatOutput>`** + `cast_mask` — match payloads:
  - `PatNode { kind: KindSpec, node_limit, post_match, force_ordered }` (no build fields).
  - `PatOutput { slot, kind: OutputKindSpec, width: Option<u32>, output_limit, capture }`
    (constraints to *check*).
  - Built by `MatcherBuilder`; consumed by `Matcher`/`walk`.
- **`Template = BiGraph<TmplNode, TmplOutput>`** — build payloads:
  - `TmplNode { kind: TemplateKind, ty: TemplateTy, capture: Option<Capture> }` (capture-only nodes
    resolve through `Bindings`; no kindspecs/limits/predicates).
  - `TmplOutput { slot, kind: OutputKindSpec }` — the **build signature** (so a multi-output interior
    node declares value/memory/control outputs and consumers wire the right slot).
  - Built by a separate, smaller `TemplateBuilder` (no `set_output_width`/`set_node_limit`/predicate
    verbs — only what construction needs); consumed by `instantiate`.

The output vertices earn their keep on **both** sides: on `Pattern` they hold match constraints; on
`Template` they hold the build signature and enable multi-output interior nodes (a built `Store`/`Call`
producing a memory token a later node consumes — owner explicitly wants multi-output supported).

`instantiate(&Template, …) -> NodeOutputId` still returns the **root's single value output** (interior
nodes may be multi-output; the root is value-producing) — unchanged contract, unchanged single-value
rewrite rule.

## Key decisions

- **Roll our own `BiGraph` over petgraph**, not a third-party bipartite-graph crate (survey briefly
  first; the existing crates are thin/immature and our needs — typed slots, two payload kinds,
  reachable-topo — are specific). No `Arc`/`Rc`/`Send`/`Sync`.
- **Two separate builders, no shared `BuilderCore`/`template` flag.** Each builder exposes only the
  verbs its side needs.
- **DRY via utilities + macros — no repetitive hand-written code** (owner mandate). The ~86 op
  factory/struct families (`Add<L,R>` + `add()` + its `MatchPat`/`TemplatePat` impls, ×every binary/
  unary/cast/cmp/float/bool variant) and the two builders' shared verb surface must be generated by
  `macro_rules!` (or shared generic helpers), not copy-pasted. The current crate already leans on
  per-family macros (`int_binary_op!`, `cast_op!`, …); extend that so adding an op or a builder verb
  is one macro line, and the `MatcherBuilder`/`TemplateBuilder` verb bodies come from one generic
  `BiGraph` surface rather than two parallel copies.
- **Uniform sub-pattern nesting via `impl Into<Pattern>`.** Control/memory/value builders' slot
  methods (`arg`/`cond`/`addr`/`data`/`with_true`/`with_false`/`preceded_by`/`mem_in`/…) accept
  `impl Into<Pattern>` and merge the sub-pattern's subgraph, with a blanket `From<P: MatchPat> for
  Pattern`. This restores the old `impl Into<Pat<Wildcard>>` uniformity (lost when the design split
  `MatchPat` from sealed `Pattern`), so `call().arg(0, load(...))` and `if_node().with_true(call(...))`
  work again. (Introduced ahead of the split during Phase 8 to unblock `complex_patterns.rs`; the
  split keeps it.)
- **Templates support multi-output interior nodes** (`TmplOutput` slots); the **root yields a single
  value**.
- `rewrite_rule_runtime(lhs: Pattern, rhs: Template)` becomes type-honest; the compile-time
  `rewrite_rule<L: MatchPat, T: TemplatePat>` is unchanged in spirit (`TemplatePat::into_template()`
  now yields a `Template`).

## Impact / scope (when executed)

- **Low churn on the typed-struct layer:** `MatchPat::compile(&mut MatcherBuilder)` and
  `TemplatePat::compile(&mut TemplateBuilder)` already lower separately; only `TemplateBuilder`'s
  output type and `into_template()`'s return change.
- **`pattern/` module:** extract `BiGraph<N,O>` + `BiVertex`/`BiEdge`; re-express `Pattern` over it;
  add `template/` graph types over it. `reachable_topo`/`assert_dag` become generic.
- **`builder/`:** split into `MatcherBuilder` (over `BiGraph<PatNode,PatOutput>`) and `TemplateBuilder`
  (over `BiGraph<TmplNode,TmplOutput>`); delete `BuilderCore` + the `template` flag + the `build`/
  `build_ty` fields on `PatNode`.
- **`template/instantiate`:** walk a `Template` (not a `Pattern`); read the build signature from
  `TmplOutput`s.
- **`rewrite/`:** `rewrite_rule_runtime` + `assert_buildable`/`check_capture_coverage` operate on
  `Template`.
- **Consumers:** strider-analyze rewrites use the compile-time `rewrite_rule(lhs, rhs)` with typed
  structs — stable. strider-py's FFI rewrite path flips its RHS handle from `Pattern` to `Template`
  (localized). Re-touch is modest, which is why doing the split after consumer migration is acceptable.

## Tests
