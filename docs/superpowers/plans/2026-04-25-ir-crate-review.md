# `ir` Crate Review Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Review the `ir` crate end-to-end for correctness bugs and simplification opportunities; fix every clippy warning; restructure `node.rs` and `graph.rs` into responsibility-scoped submodules with public paths preserved; build a layered test architecture (white-box, black-box integration, proptest invariants); merge the result into `feature/ai`.

**Architecture:** Risk-first ordering. Mechanical clippy fixes first (low-risk noise removal), then a two-pass review (correctness, then simplification) with bug fixes committed inline as TDD-style red→green→commit cycles, then the structural restructure (mechanical, on known-good code), then the test architecture build-out against the final shape. Each task is independently committable. The worktree at `.worktrees/ir-review` builds cleanly off `feature/ai @ b3da20d`.

**Tech Stack:** Rust 2021 edition, `cargo`, `proptest` (added as dev-dep in Phase 8), `cranelift-entity`, `petgraph`, `rsleigh` (path dep at `../rsleigh`).

- [ ] **Step 2: Apply the rewrite at each site**

The rewrite is mechanical:
```rust
// Before

// After
```

Watch for ordering when `f` is non-trivial — `map_or` evaluates `default` eagerly, so if the default expression has side effects or is expensive, prefer `map_or_else(|| default, f)` instead. (Realistically the existing code uses constant defaults — no real change.)

### Task 1.4: Resolve `match_same_arms` (12 sites)

**Files:** every site clippy flags. The largest cluster is in `crates/ir/src/validate/mod.rs:84` (the `output_kind_matches_expected` match).

- [ ] **Step 1: List the call sites**

```bash
cargo clippy -p ir --all-targets --no-deps 2>&1 | grep -B1 'match_same_arms' | grep -E '^\s*-->'
```

- [ ] **Step 2: Decide per-site how to resolve**

Each site falls into one of:
- **Genuinely-equivalent arms** — merge with `|`. Example: three arms returning `false` for unrelated patterns can collapse to `_ => false` *only if* the wildcard does not silently absorb a future enum variant. If the match is over a closed enum, prefer explicit listing with `|`.
- **Arms that look identical but document different intent** — keep them separate and silence the lint at the *match expression* level with `#[allow(clippy::match_same_arms)]` and a one-line comment explaining why each arm is distinct (e.g. each (expected, actual) pair represents a different type-system rule).
- **Arms that share a body but represent a real predicate** — extract a small helper that runs the dispatch once and returns a bool/value, then `match` over that.

For `validate/mod.rs` `output_kind_matches_expected` in particular: each arm encodes a different subtyping rule. The lint is misfiring there. Options:
- Refactor to dispatch through `ExpectedOutputKind::accepts(&NodeOutputKind) -> bool` and replace the `match` with a single call.
- Or annotate the match with `#[allow(clippy::match_same_arms)]` plus a doc comment.
Prefer the refactor — it makes each rule testable in isolation.

### Task 2.1: Pass 1 read of `validate/`

**Files:** `crates/ir/src/validate/mod.rs`, `layer_a.rs`, `layer_b.rs`, `layer_c.rs`, `tests.rs`.

**Invariants to carry while reading:**
- Layer A: scoped to nodes reachable via `walk_graph` (zombies skipped). Type-checks each node's outputs and inputs against `expected_signature`.
- Layer B: forward and backward use-list lists agree on every edge.
- Layer C: Entry uniqueness, InitialMemory uniqueness, ControlState predecessor kinds = Control only, ControlPhi/MemPhi token ownership and per-predecessor arity, StackStorePhi fixed arity 3, PostCall producer is the parent Call's Control output and is unique per Call.
- Aggregation: errors are accumulated into `ValidationErrors`, not fail-fast.

**Specific risks worth probing:**
- Does the reachable-set computation match `walk_graph`'s definition? A divergence would Layer-A-skip nodes that should be checked, or Layer-A-check zombies.
- Does Layer C's "phi token ownership" check actually compare token *identity* or just kind? An identity-only check is an under-restriction; a kind-only check is a miss.
- Does Layer B walk both directions, or does it implicitly trust one and verify the other?
- Does any layer panic on malformed input that should produce a `ValidationErrors` entry instead?

- [ ] **Step 1: Read the module.** Read each file top-to-bottom. Take notes (in a scratch file outside the repo, or in your head).

- [ ] **Step 2: For each suspected issue, follow the TDD red→green→commit pattern above.**

- [ ] **Step 3: If zero findings, commit the confirmation note (template above) and close the task.**

### Task 2.2: Pass 1 read of `graph.rs`

**Files:** `crates/ir/src/graph.rs` (still pre-restructure).

**Invariants to carry:**
- **Use-list bidirectionality.** Every input mutation (`add_node_input`, `remove_node_input`, `update_input`, `detach_node_inputs`, `output_use_cursor::replace*`) must update both directions of the list as a pair. A single-side update is a bug.
- **Dedup cache equivalence.** Cacheable kinds: any two `create_node` calls with identical `(kind, inputs, output_kinds)` return the same `NodeId`. Non-cacheable kinds (kinds with side-tables like `StackStorePhi`, kinds with Call semantics) must never dedup.
- **Side-table coherence.** `stack_phi_offsets` must be cleaned up when the corresponding node is detached.
- **Index stability under `remove_node_input`.** Documented behavior: re-indexes remaining inputs.

**Specific risks worth probing:**
- `output_use_cursor` — cursor invalidation correctness. After a `replace`, is the cursor positioned correctly? Is the source list fully drained on `replace_all`?
- `detach_node_inputs` — does it evict the node from the dedup cache? If not, a re-creation can return a now-invalid `NodeId`.
- `update_input` — when redirecting from `out_a` to `out_b`, both `out_a`'s consumer list (remove this input) and `out_b`'s consumer list (add this input) must update; the input's pointer must update. Three writes, all-or-nothing.
- The two `test_only_*` helpers — confirmed only used in tests; check no production caller.
- Does the `match_same_arms` refactor from Phase 1 introduce any regressions in dedup keying?

- [ ] **Step 1-3:** apply the methodology from the Phase 2 preamble.

### Task 2.3: Pass 1 read of `node.rs` + `node_signature.rs`

**Files:** `crates/ir/src/node.rs`, `crates/ir/src/node_signature.rs`.

**Invariants to carry:**
- Every `NodeKind` variant has an `expected_signature` entry.
- `NodeOutputType::is_integer()` and `is_float()` partition the value-typed variants exactly.
- `ExpectedOutputKind::AnyValue` accepts any `OutputType(_)`; `AnyInt` accepts integer-typed; `AnyFloat` accepts float-typed.
- `NodeOutputKind::OutputType(...)` is only valid for value-producing nodes.

**Specific risks worth probing:**
- Any `_ =>` arm in `NodeKind` matches in either file. Each is a future-bug surface.
- `expected_signature` for each newer kind: `CastToBool`, `CastToInt`, `CastToFloat`, `IntBitsToFloat`, `FloatBitsToInt`, `FloatToFloat`, `Piece`, `Extract`, `Insert`, `Popcount`, `Lzcount`. Do they accept the *minimal* legal input set? An over-permissive signature lets bad graphs slip past Layer A.
- `StackStorePhi { space }` arity contract — must match the `StackStorePhi has arity 3` check in Layer C.
- `Call` and `CallOther` variadic input shape — is the variadic boundary expressed in the signature, or hard-coded in the Layer C / builder?

- [ ] **Step 1-3:** apply the methodology.

### Task 2.4: Pass 1 read of `walk.rs`

**Files:** `crates/ir/src/walk.rs`.

**Invariants:**
- `walk_graph(graph, entry)` follows backward-data and forward-control edges starting from `entry`.
- Should visit every node "live" under that definition.
- Used by validate Layer A scoping and several opt passes.

**Specific risks:**
- Does it visit `PostCallMemState` / `PostCallVarState(Vn)` correctly? They consume the `Call`'s Control output.
- Does it visit `ControlPhi`/`MemPhi` tokens via the right edge (the phi-token output of `ControlState`)?
- Does it terminate on cycles? (CFG can have loops via `ControlState` → `ControlPhi` → ...)
- Are unreachable-from-entry zombies excluded as documented?

- [ ] **Step 1-3:** apply the methodology.

### Task 2.5: Pass 1 read of `builder/`

**Files:** `crates/ir/src/builder/mod.rs`, `nodes.rs`, `call.rs`, `coerce.rs`, `vars.rs`.

**Invariants:**
- Every public `build_*` method, when used per its contract, produces a graph that passes all three validate layers.
- Variable tracking: each region has a `ControlState` + per-Vn `ControlPhi`. `Vn → VarId` mapping is consistent.
- `coerce.rs` matches integer widths correctly when types differ.
- `build()` calls `validate::validate` at the end and returns its result.

**Specific risks:**
- Does any `build_*` method skip the side-table maintenance for its node kind?
- Does `coerce.rs` ever produce a `Truncate` whose output width >= input width (which would be bogus)?
- `vars.rs` — does the Vn→VarId mapping survive cross-region phi merges?
- `call.rs` — does it correctly install `PostCallMemState` and `PostCallVarState(Vn)` for caller-saved registers?

- [ ] **Step 1-3:** apply the methodology.

### Task 2.6: Pass 1 read of remaining files

**Files:** `crates/ir/src/error.rs`, `function.rs`, `region.rs`, `iterators.rs`, `lib.rs`, `ops/*`, `dot/*`.

**Invariants:**
- `error.rs` — `Result` propagation; no `unwrap`/`expect`/`panic!` in normal paths.
- `function.rs` — `BuiltFunctionGraph` is a thin newtype around `Graph`; methods don't add hidden invariants.
- `region.rs` — region IDs and their `ControlState` correspondence.
- `iterators.rs` — `Inputs`/`Outputs`/`OutputUsageIter` correctness; no infinite loops; correct iterator-trait contracts (`size_hint`, `Fused` if claimed).
- `dot/` — rendering must be deterministic and must not panic on detached zombies.

**Specific risks:**
- `iterators.rs` — fused vs not, double-end traversal correctness.
- `dot/render.rs` and `dot/label.rs` — labeling for new node kinds (`CastToBool`, `Piece`, `StackStorePhi`, etc.); missing arms render as `???` or panic.

- [ ] **Step 1-3:** apply the methodology.

- [ ] **Step 1: Write a small builder-call generator**

```rust
mod common;

use proptest::prelude::*;
use ir::node::NodeOutputType;
use ir::{FunctionBuilder, IntBinaryOp};

#[derive(Debug, Clone)]
enum Op {
    IntConst(u64),
    Add(usize, usize),   // indices into the value pool
    Sub(usize, usize),
    Return(usize),
}

fn op_seq() -> impl Strategy<Value = Vec<Op>> {
    // 1..=20 ops; each Add/Sub references existing pool indices via a
    // bounded `prop::sample::Index`. Always ends with a Return.
    proptest::collection::vec(
        prop_oneof![
            any::<u64>().prop_map(Op::IntConst),
            (any::<u8>(), any::<u8>()).prop_map(|(i, j)| Op::Add(i as usize, j as usize)),
            (any::<u8>(), any::<u8>()).prop_map(|(i, j)| Op::Sub(i as usize, j as usize)),
        ],
        1..=19,
    ).prop_map(|mut v| {
        v.push(Op::Return(0)); // Return references first value, indexed mod pool size
        v
    })
}

fn replay(ops: &[Op]) -> Option<ir::BuiltFunctionGraph> {
    let mut b = FunctionBuilder::new_raw(vec![], &[], &[], &[], None, 0).ok()?;
    let region = b.create_region().ok()?;
    b.set_entry_region(region).ok()?;
    b.set_region(region);
    let mut pool = Vec::new();
    for op in ops {
        match op {
            Op::IntConst(v) => pool.push(b.build_int_const(*v, NodeOutputType::U32)),
            Op::Add(i, j) | Op::Sub(i, j) => {
                if pool.is_empty() { return None; }
                let a = pool[i % pool.len()];
                let bv = pool[j % pool.len()];
                let kind = match op { Op::Add(..) => IntBinaryOp::Add, _ => IntBinaryOp::Sub };
                let r = b.build_int_binary_operation(a, bv, kind, NodeOutputType::U32).ok()?;
                pool.push(r);
            }
            Op::Return(i) => {
                if pool.is_empty() { return None; }
                b.build_return(Some(pool[i % pool.len()]), &[]).ok()?;
                break;
            }
        }
    }
    b.build().ok()
}
```
