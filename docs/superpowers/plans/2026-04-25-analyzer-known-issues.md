## Per-bug detail

### BUG-1 — MIPS `MULT` writes HI/LO unique varnodes never lowered to `IntBinaryOp::Mul`

**Affects:** `arithmetic::mul::{mips32le,mips32be}`, `patterns::mul_then_add::{mips32le,mips32be}`.
**Surface:** the resulting IR contains only `Entry`, `Return`, `InitialVar`, `InitialMemory` for `int mul(int a, int b) { return a * b; }`.
**Root cause:** MIPS `MULT` instruction's p-code stores its result into HI and LO unique-space varnodes (which a subsequent `MFLO` instruction then moves to a register). The analyzer doesn't model the HI/LO pair as a multiplication output that should compose into `IntBinaryOp::Mul`.
**Fix sketch:** in `strider::insn::integer.rs`, recognise the `MULT`-then-`MFLO` pattern (or directly translate `Opcode::IntMul` p-code instructions). May require a small CFG-level rewrite or a new opt pass.

### BUG-2 — CFG builder rejects MIPS DIV's CONST-space branch target

**Affects:** `arithmetic::{udiv,umod,sdiv,smod}::{mips32le,mips32be}`, `control::max_val::{mips32le,mips32be}`.
**Surface:** `Cfg build for udiv: invalid branch target variable Vn { size: 4, addr: VnAddr { off: 2, space: VnSpace { shortcut: '#' } } } at opcode PcodeInsnAddr { ... }` from `crates/cfg/src/cfg/builder/region_builder.rs`.
**Root cause:** the CFG builder's `decode_branch_target` function rejects branches whose target varnode is in CONST space — but MIPS DIV / comparison instructions encode their pc-relative branch targets as CONST-space immediates. (We handled this before for non-MIPS archs because their relative-branch encoding sits in the default code space, not CONST.)
**Fix sketch:** in `crates/cfg/src/cfg/builder/region_builder.rs`, extend `decode_branch_target` to handle CONST-space relative branches (interpret the CONST offset as a signed pcode-instruction-index delta).

### BUG-3 — Comparison emits Bool to AnyInt-expecting node (MIPS + ARM)

**Affects:** `control::clamp::{mips32le,mips32be}`, `control::factorial::{mips32le,mips32be}`, `control::early_return::arm`, `globals::runtime_const_idx::{mips32le,mips32be}`.
**Surface:** IR validation fails: `node node177 input[0] has kind OutputType(Bool), expected AnyInt`.
**Root cause:** integer-comparison p-code emits a Bool output, but downstream the IR builder (or an opt pass) is using that bool as an integer input to an arithmetic op — likely an arch-specific lowering that uses comparison results in branches *and* in arithmetic without an explicit `CastToInt`.
**Fix sketch:** identify the missing `CastToInt` site in `analyzer::insn` or `opt::known_bits`. Audit `expected_signature` against actual emissions.

### BUG-4 — ARM conditional select non-Bool

**Affects:** `control::select_three::arm`.
**Surface:** `analyze_cfg` error: `"output %55 is not a bool value"`.
**Root cause:** ARM's `IT`/`CSEL` lowering for `if (sel == 0) return a; if (sel == 1) return b; return c;` emits a non-Bool value where the IR builder expects Bool for the `If` node's condition input.
**Fix sketch:** insert a `CastToBool` at the appropriate site, or handle the ARM-specific p-code shape in `handle_cond_branch`.

### BUG-5 — `BranchIndirect` p-code opcode unimplemented

**Affects:** `control::nested_loops::arm`, `calls::apply_indirect::{aarch64,arm,mips32le,mips32be}`, `abi::tail_caller::arm`.
**Surface:** `unimplemented p-code opcode BranchIndirect at crates/strider/src/strider/insn/mod.rs`.
**Root cause:** `Opcode::BranchIndirect` is not in the `process_insn` opcode dispatch.
**Fix sketch:** add a `handle_branch_indirect` to `strider::insn::control.rs`, similar to `handle_call_indirect` but emitting an indirect branch. Will likely need CFG support for indirect branch targets too (possibly opening up jump-table reconstruction work).

### BUG-6 — Compiler tail-call elision drops Call nodes

**Affects:** `calls::fib_recursive::*`, `calls::pass_through::*`, `stack::recursive_stack_growth::*`, `patterns::recursive_with_accumulator::*`.
**Surface:** `count_calls(g) >= N` assertions fail because tail-call optimisation converts recursive calls into branches.
**Root cause:** **Test design issue, not analyzer bug.** With `-O2`, GCC tail-calls `fib(n-2)` and `pass_through(x)→leaf(x)` directly. Mitigation options: (a) compile fixtures with `-fno-optimize-sibling-calls`; (b) relax assertions to accept either Call OR a recursive branch back to the function entry. Option (b) is cleaner — it asserts what the analyzer must produce, not what the compiler must emit.

### BUG-7 — Indirect call follows fn-pointer into unmapped memory

**Affects:** `calls::apply_indirect::{x86,x64}`.
**Surface:** `MemReadErr` at `0x4012eb` during CFG construction.
**Root cause:** the CFG builder follows the function-pointer's address through memory; when the address is computed at runtime and the constant base happens to land in unmapped memory, the read fails.
**Fix sketch:** in `cfg::Builder`, treat indirect-call targets as opaque (don't recursively expand the CFG into the unknown destination). Likely a one-line guard.

### BUG-8 — Float arithmetic not lowered to `FloatBinaryOp`

**Affects:** `floats::{f32,f64}_arith::all-archs`.
**Surface:** zero `FloatBinaryOp` nodes in the IR.
**Root cause:** unknown — needs investigation. Possible: hardware float ops (SSE2 `ADDSS`, `MULSS`, etc.) emit p-code that doesn't reach the `process_float_binary_op` dispatch. Inspection should start at `strider::insn::float.rs` to see whether the FP opcodes are reaching the dispatch at all, then move to `rsleigh` if they aren't being lifted.

### BUG-9 — Float conversion lowering panics with type errors

**Affects:** `floats::{f32_to_f64,f64_to_f32,float_to_int,int_to_float}::all-archs`.
**Surface:** `crates/ir/src/builder/nodes.rs: "output %N is not a float value"`.
**Root cause:** `strider::insn::float::handle_float_int_to_float` (and siblings) calls `build_int_to_float(int_input, float_ty)` but `int_input` is not actually an integer-typed value at that point — it has come through `read_vn` which may have produced a float-typed value (especially for floating-point register reads).
**Fix sketch:** insert a `convert_to_int_if_needed` before the `build_int_to_float` call, or use `read_vn`'s typed variant.

### BUG-10 — Float comparison emits Bool to AnyInt

**Affects:** `floats::{f32,f64}_compare::all-archs`.
**Surface:** same as BUG-3 but for float comparisons.
**Root cause:** float-comparison p-code emits a Bool used downstream as an integer.
**Fix sketch:** related to BUG-3; same `CastToInt` audit.

### BUG-11 — Float negation not lowered to `FloatUnaryOp::Neg`

**Affects:** `floats::f32_neg_abs::all-archs`.
**Surface:** zero `FloatUnaryOp::Neg` nodes; the negation is emitted as a XOR with the sign bit.
**Root cause:** `-x` for float is implemented as `x ^ 0x80000000` at the bit level, which is a regular `IntBinaryOp::Xor` after `FloatBitsToInt`. **May not be a bug** — this is the canonical lowering. Recommendation: relax the assertion to accept either `FloatUnaryOp::Neg` OR the `Xor`-with-sign-bit pattern.

### BUG-13 — AArch64 128-bit constant for array init

### BUG-15 — `__builtin_popcount` not recognised

**Affects:** `builtins::{popcount32,popcount64}::all-archs`.

**Fix sketch:** verify with `objdump -d fixtures/out/x64/builtins.elf` what `popcount32` actually compiles to. Then check whether rsleigh's x86_64.sla recognises the encoding.

### BUG-19 — `IMUL` result chain breaks pattern data-flow

### BUG-20 — `KnownBits`/`ConstFold` collapses XOR chain prematurely

**Affects:** `patterns::chained_xor_mask::{x86,x64,aarch64,arm}`.
**Surface:** `xor(and(xor(_,c), c), c)` returns 0 matches.
**Root cause:** with `-O2`, GCC may pre-fold the XOR chain since the constants are known at compile time. The optimizer pipeline's `ConstantFold` then collapses the result into a single masked XOR.
**Fix sketch:** test design issue — make the input non-constant so the chain survives.

### BUG-21 — 32-bit `IntConst(-50)` sign-extension

**Affects:** `patterns::if_returns_const::{arm,mips32le,mips32be}`.
**Surface:** neither `(-50i32) as u32 as u64 == 0xffffffc6` nor `(-50i64) as u64 == 0xffffffffffffffce` appears in the graph. The 32-bit ABIs sign-extend differently.
**Root cause:** on 32-bit archs, the IR may store `-50` as `0xffffffce` (sign-extended to 64 bits) but the analyzer's `IntConst` may store it as `0xffffffc6` (unsigned 32-bit). Discrepancy in width handling.
**Fix sketch:** test design issue — accept any of the three forms.

### BUG-28 — Calling-convention machinery: incomplete arg-slot connectivity

**Affects:** every `forward_*` / `narrow_widths` / `mixed_4` test in `crates/strider/tests/calling_convention.rs` on `aarch64be`, `ppc32{be,le}`, `ppc64{be,le}`, `mips64{be,le}`, `x86` (cdecl), and (for `forward_8`/`forward_16` only) `x64`.

**Surface (two related issues):**
1. The IR `Call` node's positional arg-input list does not include the calling convention's full register-arg list.  When the function reads an arg-passing register only at sub-register width (e.g. `EDI` on x64 with `int a` parameter, never `RDI`), the IR builder's `arg_passing_vars` filter (`upgrade_to_tracked` in `crates/ir/src/builder/mod.rs:214-235`) drops that arg-passing register because no tracked variable *covers* it (only contained-in matches exist).  Consequently the `Call` node has fewer positional arg slots than `arg_passing_regs.len()`, and `pattern::call().arg(i, function_arg(i))` cannot match for those dropped slots.
2. `CallStackArgCollect`'s memory-chain walk requires a contiguous chain of `StackStore` nodes leading into the `Call`.  When unrelated stores (e.g. volatile global stores from a fixture's "force live" barriers) are interleaved with stack-arg pushes, the walk terminates at the first non-`StackStore`, missing the stack-passed args entirely.

**Root cause:** Two compounding issues.

1. `detect_register_args` (commit `f179c7f`) correctly emits a `FunctionArg` node via the **sub-register fallback** when only a contained-in `InitialVar` exists — so the `FunctionArg(i)` *node* gets created and rewires existing uses of the narrow `InitialVar`.  But the `Call` node's input list was already wired at `build_call` time (`crates/ir/src/builder/call.rs:23-27`) to the filtered `arg_passing_vars`, which omitted the dropped arg-passing register.  No subsequent pass adds the missing arg slot back.
2. `CallStackArgCollect` (`crates/opt/src/stack_store/call_args.rs`) is conservative by design: any non-`StackStore` on the memory chain terminates collection.  This protects against misidentifying frame locals as args, but breaks when the optimiser chooses to interleave volatile global stores with arg pushes — which gcc/clang at `-O2` do freely.

**Fix sketch:** Two complementary fixes are needed.

1. **Fix #1 (Call arg-slot completeness):** extend `detect_register_args` to ALSO append a missing arg slot to each `Call` node in the function when the corresponding arg-passing register is filtered out at FunctionBuilder time.  The FunctionArg already exists (via sub-register fallback); the rewire just needs to be done at every existing Call site too.  Alternatively, lift the `arg_passing_vars` filter so dropped arg regs are kept as `InitialVar(arg_reg)` placeholders (with no consumers) and let `detect_register_args` later rewire them.

### BUG-29 — `arm_be` VFP register file laid out in reverse byte order

**Affects:** every float-subsystem test on `arm_be` —
`floats::{test_f32_arith, test_f32_compare, test_f32_neg_abs, test_f32_to_f64, test_f64_arith, test_f64_compare, test_f64_to_f32, test_float_to_int, test_int_to_float}`.

**Surface:** the analyzer-built IR for any function that uses VFP (`f32_arith`, `f64_arith`, `int_to_float`, …) on `arm_be` contains 0 `FloatBinaryOp` / `FloatToFloat` / `FloatToInt` / `IntToFloat` nodes — only `Entry`, `FunctionArg`, `Return`, `InitialMemory`, `InitialVar`, and a few `StackStore`s.  The CFG's p-code reflects the actual `vadd.f32` / `vmul.f32` / `vdiv.f32` ops correctly, so the gap is between p-code and IR.

**Root cause:** Sleigh's `ARM8_BE` SLA spec describes the VFP register file in reverse byte order — under BE the `s_n` offsets descend (`s0 = off 892`, `s1 = off 888`, …, `s31 = off 768`) and the d/q wide views don't sit at the same start byte as their `s_*` constituents (`d0 = off 1016`, not `off 892`).  This is a Sleigh modelling choice for 32-bit ARM BE that mirrors how AAPCS lays VFP regs in BE memory.  But the strider analyzer's `find_largest_fitting_register` / register-aliasing logic assumes the container register's start byte equals the smallest sub-register's start byte (true for x86 `rax/eax/ax/al`, AArch64-LE `q0/d0/s0`, and ARM-LE `q0/d0/s0`).  Under that assumption no read of `s0` is ever recognised as reading any larger tracked register, and no write of `s0` aliases any read of `d0`.  The analyzer therefore drops every VFP read-write chain.

**Per-bug list of failing tests** (each carrying `BUG-29: …` reason):
* `floats::test_f32_arith::arm_be`
* `floats::test_f64_arith::arm_be`
* `floats::test_f32_compare::arm_be`
* `floats::test_f64_compare::arm_be`
* `floats::test_f32_to_f64::arm_be`
* `floats::test_f64_to_f32::arm_be`
* `floats::test_int_to_float::arm_be`
* `floats::test_float_to_int::arm_be`
* `floats::test_f32_neg_abs::arm_be`

**Fix sketch:** two avenues, neither cheap:
1. Extend `strider::register_aliasing::find_largest_fitting_register` to handle BE-descending register banks (recognise that `s0` at `off 892` is the high-half slot of `d0` at `off 1016`, not the low-half).  Requires teaching the aliaser about per-bank endianness, since GP regs `r0..r15` are NOT laid out in reverse — only the VFP bank.
2. Translate Sleigh's BE VFP varnode addresses to a synthetic ascending layout in the analyzer's adapter (a one-shot rewrite of `Vn { off }` for the 256-byte VFP bank: `off' = base + (top - off) - size`).  Less invasive in `register_aliasing` but trickier for users who inspect raw varnodes.

Either fix should restore the LE-matching IR for all 9 float tests.  Until then, every `arm_be` float test is gated on `ignore = { ArmBe: "BUG-29: …" }` in `crates/strider/tests/floats.rs`.
